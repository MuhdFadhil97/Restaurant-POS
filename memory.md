# POS Project — Memory

## Project Summary
Web-based Point of Sale system for a retail/F&B business, designed to support multiple outlets/branches under one company from day one. Roles: `admin`, `manager`, `cashier`, `kitchen` (kitchen added 2026-09-16 Phase 7).

Stack: Node.js/Express (REST API, JWT auth) + React/Vite (React Router, TanStack Query, Zustand) + PostgreSQL/Prisma + Tailwind CSS + Docker Compose. Backend and frontend written in **TypeScript**.

Scope confirmed at kickoff (2026-09-16):
- **Multi-outlet from day one** — outlet switcher, per-outlet stock, cross-outlet reporting are in v1, not deferred.
- **F&B with table management** — tables, open tabs (transactions attached to a table before payment), not pure retail.
- ~~Loyalty points deferred~~ — **built in Phase 7** (2026-09-16): see Key Decisions below. Left here for history; do not treat as still-deferred.
- **Receipts: HTML only** — printable/emailable HTML receipt in v1; thermal/ESC-POS printer support still deferred.

Phase 7 (2026-09-16) added four more areas on top of the original v1 scope, at the user's request after reviewing a recommendation menu: Kitchen Display System, Supplier/Purchasing + multi-outlet stock transfer, Loyalty/Promotions/Gift Cards, and User Access Management (audit trail + lockout). See Key Decisions and Session Log below.

## Key Decisions
- **2026-09-16 — TypeScript on both backend and frontend.** Reason: pairs naturally with Prisma's generated types and the "production-grade" bar set by the prompt; not explicitly requested but a safe, standard default. Flagged to user as an assumption.
- **2026-09-16 — Role as a Prisma enum (`admin/manager/cashier`), not a `roles` table.** Reason: roles are fixed and not tenant-customizable in this system; a table would add join overhead for no configurability benefit. If custom/configurable roles are ever needed, this will need to change to a table + permissions model.
- **2026-09-16 — Product catalog is shared across outlets; only stock is per-outlet.** Reason: for a multi-outlet chain, products/categories/pricing are normally managed centrally, while stock quantity naturally varies per location. Modeled via a `ProductStock` join table (productId + variantId? + outletId) rather than a `stockQuantity` column directly on `Product`.
- **2026-09-16 — "Hold/park" and F&B "open tab" share one model.** A `Transaction` with status `HELD` (parked, no table) or `OPEN` (attached to a `Table`, still accumulating items) covers both use cases described separately in the prompt, avoiding a duplicate concept.
- **2026-09-16 — Users can be granted access to multiple outlets via a `UserOutlet` join table**, rather than a single `outletId` FK on `User`. Reason: needed for managers/admins overseeing multiple outlets under the multi-outlet-from-day-one decision. Cashiers typically get exactly one grant.
- **2026-09-16 — Customers are company-wide, not per-outlet.** Reason: a customer should have one purchase history across all outlets of the chain, not siloed per branch.
- **2026-09-16 — Tax-exclusive pricing; order-level discount applied after tax.** Product `unitPrice` excludes tax; tax is computed per line from the product's `TaxRate` and added on top. An order-level discount reduces the final total but is applied after per-line tax is computed (not redistributed into the taxable base). This is a v1 simplification — revisit if strict tax-on-discounted-price compliance is required for a given jurisdiction. Implemented in `backend/src/modules/transactions/calculations.ts` and mirrored in `frontend/src/features/pos/cartMath.ts` for the live cart preview (both round to 2dp with the same `round2` helper to avoid float-precision drift).
- **2026-09-16 — Hold/park and F&B checkout share one atomic-transaction design.** `POST /transactions/checkout` is the fast one-shot path (create + decrement stock + pay, all atomic) used for walk-in retail sales. `POST /transactions` (no payment) creates a draft — `HELD` if no table, `OPEN` if a table is attached — and `POST /transactions/:id/finalize` pays an existing draft later. Stock is only decremented at the point of payment (checkout or finalize), never when a draft is created or items are added, so drafts can be edited freely without stock-reservation bookkeeping.
- **2026-09-16 — Void/refund approval: manager/admin can self-approve; cashier must supply another user's credentials.** A cashier voiding/refunding a transaction must pass `approverId` + `approverPassword` of a manager/admin, verified server-side via bcrypt against that user's password hash (see `resolveApproval` in `backend/src/modules/transactions/service.ts`). Refunds are full-transaction-only in v1 (no partial refund of individual line items).
- **2026-09-16 — Receipt template settings live on `Outlet`** (`receiptLogoUrl`, `receiptFooter`) rather than a separate table, since they're simple per-outlet config, not a versioned or reusable "template" concept in v1.
- **2026-09-16 — Phase 7: promotions are rule-validated discounts, not a full auto-apply engine.** `Discount` gained `minSpend`/`startDate`/`endDate`/`usageLimit`/`usageCount`/`productId`/`categoryId`. A cashier still manually picks a discount (no automatic "best offer" selection), but eligibility (active, in date window, under usage limit, min spend met, product/category scope for line-level) is validated server-side at checkout/finalize time — not on every draft edit — and `usageCount` only increments on a completed sale, so abandoned carts don't burn through a limited promo. See `validateAndConsumeDiscounts` in `backend/src/modules/transactions/service.ts`.
- **2026-09-16 — Phase 7: loyalty points and gift cards settle inside the same DB transaction as checkout/finalize**, not as separate calls. `Outlet.loyaltyEarnRate`/`loyaltyRedeemRate` (per-outlet, defaults 1 point/$1 earned, $0.01/point redemption value) drive `accrueLoyaltyPoints`/`processPayments` in `transactions/service.ts`. A `GIFT_CARD` payment's `reference` field carries the card's code (looked up and debited atomically); `LOYALTY_POINTS` payment requires `transaction.customerId` and converts the paid amount to points via the redeem rate. Reason: keeps balance mutations exactly as atomic as the stock decrement they sit next to — no separate non-transactional step that could desync from the sale.
- **2026-09-16 — Phase 7: KDS prep status lives directly on `TransactionItem`** (`prepStatus` enum + three timestamp columns) rather than a separate `KitchenOrder` table, since a kitchen ticket *is* the transaction item, just viewed from the kitchen's side — avoids duplicating quantity/product data. `Product.stationId` (optional) routes an item to a `KitchenStation`; items with no station show up in the unfiltered "All Stations" KDS view.
- **2026-09-16 — Phase 7: added a `KITCHEN` role** rather than reusing `CASHIER` for kitchen staff, since kitchen staff shouldn't have checkout/payment access. `KITCHEN` users land on `/kds` after login (see `getHomeRoute` in `frontend/src/lib/roleHome.ts`) and can access no other route; every other role can also view `/kds` (e.g. a cashier checking prep status).
- **2026-09-16 — Phase 7: account lockout is 5 failed attempts → 15-minute lock**, tracked via `User.failedLoginAttempts`/`lockedUntil` (reset to 0/null on any successful login). Auth events (`LOGIN_SUCCESS`/`LOGIN_FAILURE`/`ACCOUNT_LOCKED`) and admin-driven user changes (`USER_ROLE_CHANGED`/`USER_PASSWORD_CHANGED`/`USER_OUTLET_ACCESS_CHANGED`) reuse the existing `AuditLog` model rather than a new table — it already supports arbitrary `action`/`details`. A login attempt against a *nonexistent* identifier is not audited (no valid `userId` to attribute it to, and logging it would be a username-enumeration side channel).
- **2026-09-16 — Product Categories got their own Settings tab** (`frontend/src/features/settings/CategoriesTab.tsx`), list/rename/delete via new `useUpdateCategory`/`useDeleteCategory` hooks — the backend (`backend/src/modules/categories/`) already had full CRUD since the very first build; only the frontend was missing. Rename uses an inline text-input toggle per row rather than a modal, since it's a single-field edit. The existing quick-add-category textbox inside `ProductForm.tsx` was left as-is (still convenient mid-product-creation) — both share the `["categories"]` TanStack Query key, so changes in either place show up in the other immediately.
- **2026-09-16 — Suppliers tab gained Edit/Delete.** Unlike Categories (single field → inline edit), Supplier has 5 editable fields, so edit reuses a modal form (`SupplierFormModal`) shared between create and edit — same shape as `OutletsTab.tsx`'s `OutletFormModal`. This is now the established convention in this codebase: **single-field entities get inline row editing (Categories); multi-field entities get a shared create/edit modal (Outlets, Users, Suppliers, Tables).** Delete uses a plain `window.confirm()` rather than a custom confirmation modal, since this is a low-stakes, easily-undone admin action (soft-delete, not destructive to transaction history) — reconsider if a higher-friction confirm is ever wanted.
- **2026-09-16 — Tables tab gained Edit/Delete, same modal convention.** `TableFormModal` is shared between create and edit; its `status` field (AVAILABLE/OCCUPIED/RESERVED) only renders when editing an existing table — a brand-new table always starts `AVAILABLE` server-side, so exposing status at creation time would be a meaningless extra field. This is the third tab (after Categories, Suppliers) to go from create+list-only to full CRUD on direct request — a pattern worth anticipating: **when a Settings tab is first built, consider building Edit/Delete alongside Create/List from the start**, since the user has asked for it on every multi-field CRUD tab so far.
- **2026-09-16 — Discounts and Gift Cards tabs also got Edit/Delete, same modal convention, fix applied proactively.** Both new `DiscountFormModal`/`GiftCardFormModal` were written with the `useEffect(() => { if (open) {...} }, [open, initial])` re-seed from the very first version — no separate bug-fix pass needed this time, since the pattern was already documented from the Outlets/Users/Suppliers/Tables fix immediately prior. **Gift cards have no backend `DELETE` route on purpose** — a card can hold real balance and is referenced by past `Payment.giftCardId` rows, so "Delete" in the UI calls the existing `PATCH .../gift-cards/:id` with `{isActive: false}` instead (deactivate, not erase); the Delete link is hidden once a card is already inactive, and the `code` field is disabled in the edit form (a card's code is its identity — shouldn't change post-issuance, only `balance` and `isActive` are editable).
- **2026-09-16 — Fixed a recurring bug class: "create/edit modal" components must re-seed their fields on open, not just on first mount.** `OutletFormModal`, `UserFormModal`, `SupplierFormModal`, and `TableFormModal` all followed the pattern `const [x, setX] = useState(initial?.x ?? "")` — correct only for a component that mounts fresh every time. But their parent tabs render the "edit" instance of the modal *unconditionally* (`<XFormModal open={!!editing} initial={editing ?? undefined} .../>`), so it mounts once on first page load with `initial=undefined`, and later prop changes to `initial` (when a different row is clicked) never re-run the `useState` initializer — the fields stayed blank or showed the previous row's values. This is the identical root cause as the `PaymentModal` bug found earlier in this build (documented under [[verify-ui-by-driving-it]]); I didn't generalize the fix to the Settings tabs when I wrote them, and it took a direct user bug report to catch it since it's invisible to type-checking. **Fixed by adding `useEffect(() => { if (open) { ...reset every field from initial... } }, [open, initial])` to all four.** `ProductForm`'s edit path was already safe by accident — `ProductsPage.tsx` renders it as `{editing && <ProductForm initial={editing} .../>}`, which unmounts/remounts on every edit target change instead of reusing one instance. **Going forward: any new create/edit modal in this codebase needs either the `useEffect` re-seed or the conditional-unmount pattern — check for this proactively instead of waiting for a bug report.**

## Architecture Notes
- Every transactional table (`Transaction`, `TransactionItem`, `Payment`, `InventoryMovement`, `CashSession`, `AuditLog`, `Table`, `ProductStock`, `TaxRate`) carries `outlet_id`, per the prompt's multi-outlet-readiness requirement.
- Checkout (cart → stock decrement → transaction + items + payments) runs inside a single Postgres transaction (Prisma `$transaction`) — not app-level-only logic.
- Roles enforced at both API (middleware route guards) and UI (conditional rendering/routing) layers.
- Financial records (`Transaction`, `Payment`) are never hard-deleted; they use `status` (COMPLETED/VOIDED/REFUNDED) instead of soft-delete. Soft-delete (`deleted_at`) is reserved for master data (products, categories, customers, users).

## Conventions
- Primary keys: UUID, stored as native Postgres `uuid` columns (`@id @default(uuid()) @db.Uuid`) — every FK field carries `@db.Uuid` too, including polymorphic ones like `AuditLog.entityId`. (Initially the schema used plain `String` without `@db.Uuid`, which Prisma maps to `text`; changed 2026-09-16 per user request to use proper native `uuid` columns instead of text.)
- Icons: hand-rolled inline SVG components in `frontend/src/components/icons.tsx` (24x24 viewBox, stroke-based) rather than an icon library — no `lucide-react`/`heroicons`/etc. dependency was ever added, so keep using this file's pattern (a shared `Icon` wrapper + one named export per icon) for any new icon rather than reaching for a new package.
- Timestamps: `created_at` / `updated_at` on every table; `deleted_at` nullable soft-delete on master-data tables only. Financial records use `status` instead (see Architecture Notes).
- API error shape: `{ error: { message: string, code: string, details?: unknown } }` — see `backend/src/lib/apiError.ts` and `backend/src/middleware/errorHandler.ts`. Prisma known-request errors (P2002 unique conflict, P2025 not found) are mapped to this shape too.
- Validation library: Zod, applied via a `validate({ body?, query?, params? })` middleware per route (`backend/src/middleware/validate.ts`). Convention: each module's `validation.ts` exports the *body* schema directly (not wrapped in `{body: ...}`).
- Frontend: TanStack Query hooks live in `frontend/src/api/*.ts`, one file per backend module, each exporting `use<Noun>()` queries and `use<Verb><Noun>()` mutations. Zustand stores (`authStore`, `outletStore`) are persisted to `localStorage`.

- **2026-09-16 — Currency display is `RM` (Malaysian Ringgit), centralized in one place.** The `money()` helper in `frontend/src/features/pos/cartMath.ts` returns the full formatted string including the `"RM "` prefix — callers just do `{money(x)}`, never re-add a symbol. This was a deliberate refactor away from the original pattern (every call site hardcoding a literal `$` next to `{money(x)}`) specifically so a future currency change is a one-line edit, not a 40-site find-replace. **Any new money display must call `money()` and render its result as-is — never prepend a currency symbol at the call site.**
- **2026-09-16 — Found and fixed a latent bug while verifying the currency change: Reports page raw SQL was broken since the UUID migration.** `backend/src/modules/reports/service.ts`'s two `$queryRaw` calls (`salesSummary`, `topProducts`) compare `outlet_id` (now a native `uuid` column, see the 2026-09-16 UUID-migration entry above) against `${query.outletId}`, which Prisma sends as a `text`-typed bind parameter — Postgres has no `uuid = text` operator, so both queries 500'd. This had been silently broken since the UUID migration; the end-to-end verification pass done at that time exercised checkout/inventory but not the Reports page specifically. Fixed with an explicit `::uuid` cast at both interpolation points. **Lesson: `$queryRaw`/`$executeRaw` call sites need to be re-audited any time a column's underlying Postgres type changes** — Prisma's typed query builder (used everywhere else in this codebase) handles that automatically, but raw SQL doesn't.
## Known Issues / Deferred Items
- Thermal/ESC-POS printer integration — deferred past v1; HTML receipt only.
- Void/refund approver identification is a raw user-ID text field (see `frontend/src/features/transactions/VoidRefundModal.tsx`) — works but isn't cashier-friendly; a username lookup or manager PIN pad would improve UX.
- Cash session reconciliation (`backend/src/modules/cashSessions/service.ts`) sums cash payments during the session window but does not subtract cash refunds issued during that window — a session with a cash refund will show `expectedCash` slightly high. Low priority for v1 given refunds are expected to be rare and manually reconciled.
- Refunds are all-or-nothing (whole transaction) — no partial/line-item refund in v1.
- No automated test suite yet (Vitest is scaffolded in `backend/package.json` but no test files exist). Verification so far has been manual/scripted (see planning.md "Verified End-to-End").
- **Phase 7 additions not yet built** (see the module-recommendation plan for full list): configurable/granular permissions beyond the 4 fixed roles, session/device revocation (JWTs are still fully stateless — no server-side session table), self-service password reset and email-based user invitations (both need an email-sending integration this project doesn't have at all yet).
- **Refunding a transaction does not reverse its loyalty points or gift-card debit.** If a completed sale earned points, redeemed points, or was paid via gift card, refunding it restocks inventory (existing behavior) but leaves the customer's points balance and any gift card balance unchanged. Same category of gap as the pre-existing cash-session-refund note above; not fixed in this pass due to time — flag if refunds involving loyalty/gift-card payments become common.
- **Promotion product/category scoping is line-level only.** An order-level `Discount` with `productId`/`categoryId` set is not evaluated against the order's contents (see the comment above the scope-checking loop in `validateAndConsumeDiscounts`) — in practice, only set those scope fields on `LINE`-scope discounts.
- KDS has no real-time push (WebSockets); it polls every 5s (`useKdsQueue`'s `refetchInterval`), same pattern as the table-status polling. Fine for a single-kitchen-screen v1; would need a socket layer to feel instant at higher order volume.

- **2026-09-16 — Floor Plan tab: unsaved drag edits leaked across outlet switches.** `FloorPlanTab.tsx`'s `pending` map (table id -> dragged posX/posY) was only ever cleared by Save/Discard, not by switching the active outlet. Since the `dirty` flag is just `Object.keys(pending).length > 0`, dragging a table in Outlet A and then switching to Outlet B (without saving/discarding) left "Save Layout"/"Discard" both enabled for Outlet B even though nothing there had changed — confirmed visually via a Playwright repro. Harmless data-wise (stale pending entries key by Outlet A's table ids, which don't exist in Outlet B's list, so a stray Save is a no-op resend), but misleading UX. Fixed with `useEffect(() => setPending({}), [outletId])`. Same root cause category as the modal re-seed bug class below (local state not reset when an identifying prop/id changes) — worth checking any other per-outlet local UI state for the same gap.
